## Objective and boundaries

Effort escalation currently depends on three modules that each decide what counts as a verifier run. This plan makes `EffortEvidence` the single owner: it classifies one finished tool call, stamps the verifier, order and revision, and records the resulting effort state in one transaction. Both callers hand it raw facts and keep their own scheduling.

In scope: verifier identity, evidence ordering, revision semantics at settlement, the harness's command selection, the store write, tests for those, and the documents that describe them.

Out of scope: the status/transition duplication and the `packages/ai` findings from the same architecture review; any change to the vendored policy rules or `EFFORT_POLICY_PROTOCOL_VERSION`; the other users of `Bus.latestSequence` and `Bus.reserveSequence` (`session/title.ts:140`, `session/projector.ts:257`, `session/transfer.ts:144`, and the event bus itself), which are correct for event sequencing and stay untouched; committing.

- `bumpRevision` has eight test call sites and one production call: `verify.test.ts` 111, 128, 150, 188, 233, 271; `store.test.ts` 93, 107; production at `evidence.ts:36`.
- `setLevel` has five test call sites and one production call: `verify.test.ts:149`; `store.test.ts` 64, 109; `evidence.test.ts` 191, 208; production at `evidence.ts:74`.
- `setOpenFailure` has one test call site (`store.test.ts:108`) and one production call (`evidence.ts:71`).
- `recordSelection` only updates `last_applied_variant` on conflict, so it cannot clobber an evidence write (`store.ts:120-123`).
- Migrations are generated by `bun run migration --name <name>` and contain only `up(tx)`; the transaction wrapper is applied by the migration runner (`migration.ts:111-118`), and `--check` detects an ungenerated migration, a stale schema snapshot, and a stale registry (`script/migration.ts:63-91`).
- The event counter table is `event_sequence`, keyed by `aggregate_id` with column `seq` (`event/sql.ts:4-8`).
- The evidence path currently borrows that counter: `Bus.latestSequence` returns `-1` for a missing row (`bus.ts:32`), and `Bus.reserveSequence` writes `max(existing, seq)` into `event_sequence` (`bus.ts:45`). Every evidence observation therefore advances the session's event sequence.
- `step.ts` calls `matchVerifier` before execution to decide whether a shell call counts as a mutation (`step.ts:141-147`).
- The harness prefers `row.openFailure.verifier` when it is configured, before falling back to the first entry (`verify.ts:57-61`).
- The policy clears an open failure only for the same verifier, at a strictly newer sequence and an equal-or-newer revision (`policy/policy.ts:90-97`).
- `EffortStore.Interface` is consumed outside `store.ts` by `evidence.ts:25`, `verify.ts:19`, `transition.ts:36`, and `delegation.ts:61`, all through methods that survive this change.

Assumptions, each covered by a test:

- Store methods called inside `db.transaction` join that transaction. Effect's statement executor resolves the transaction from fiber context and the Drizzle wrapper installs it, so the claim and the state write commit together.
- SQLite serializes the two statements on one connection, so two concurrent claims receive different numbers.

## Technical approach

**Owner interface.** `EffortEvidence` exports three things: the classification function, `matchVerifier`, and `warnUnmatchable`. Classification takes resolved settings and a raw settlement (tool, input, metadata) and returns none, pass, or fail, plus the matched verifier. It performs no I/O and reads no config. `matchVerifier` stays exported because the dispatch path genuinely needs the same predicate (`step.ts:141-144`); that is one implementation with two call sites, not two owners.

**Ordering.** Add `evidence_sequence` to `session_effort`, not null, default 0. The column is internal to the store and is **not** added to `Info`. `claimSequence` returns the number, so `Info`, `fromRow`, and every existing `set({ ... })` literal stay unchanged. Order of operations inside one transaction:

1. `claimSequence(sessionID, expectedRevision?)` runs `UPDATE session_effort SET evidence_sequence = evidence_sequence + 1 WHERE session_id = ? AND revision = ?`, then reads the new value. No row updated means discard. The revision clause is present only when an expected revision is supplied. A missing effort row therefore records nothing, which is what the current code already does; the row is created when the session's level is first chosen, before any tool runs.
2. `get(sessionID)` reads the fresh state, now protected by the write lock.
3. `applyEvidence` runs with the claimed sequence and the fresh revision.
4. `recordEvidence` writes open failure, level and clean passes in one update.

**Revision.** The dispatch path keeps `bumpWorkspaceRevision` (`step.ts:147`) and stops passing `startedMutation`. The settlement path stops bumping. `mutating_tools` is read only at dispatch.

**Matching.** Identity stays a bare command with exact match and no cwd. `warnUnmatchable(settings)` dedupes by command string and is called by both callers where they resolve settings.

**Harness command selection.** The policy requires the same verifier to clear a failure, so the harness must not simply take the first configured entry. In order:

1. If `row.openFailure` names a configured verifier, that command is the candidate.
2. Otherwise the candidate is the first configured entry that `matchVerifier(cmd, [cmd])` accepts.
3. If the failure's verifier is configured but not a simple command, warn once and run nothing. No other command can clear that failure, so running one would burn a verifier run per idle pass and never recover.
4. If no configured entry is simple, warn once per distinct invalid entry and run nothing.

**Settings.** Callers resolve once per step and once per idle pass. `observe` takes `{ db, efforts }` plus the resolved settings, and no longer imports `Config`.

**Store.** Final interface, seven methods: `get`, `set`, `recordSelection`, `claimSequence`, `recordEvidence`, `setVerdict`, `bumpWorkspaceRevision`. Deleted: `setOpenFailure`, `setLevel`, `bumpRevision`.

**Documented alternative, not adopted.** Replace `claimSequence` + `recordEvidence` with one `recordEvidence(sessionID, expectedRevision, decide)` that runs a conditional update and retries when the revision moved. That keeps six methods but moves a retry loop into the store and makes the discard path less obvious. It would change only Task 3 and its tests, so it remains available if you prefer it.

    (SELECT seq FROM event_sequence WHERE aggregate_id = session_effort.session_id), -1));`)

## Release and recovery

The change is additive. The new column has a default, so reverting the code leaves an unused column that harms nothing. There is no destructive migration and no data rewrite beyond the backfill. If the backfill proves wrong, the recovery is a follow-up migration that recomputes the column from `event_sequence`; the original rows are untouched.

Migrations run at startup against the local database. No deployment step exists for this fork beyond building the app.

## Acceptance criteria

All of these must hold:

- The model path and the harness produce identical evidence state from identical facts.
- A pass clears a failure only when it is newer, from the same verifier, and from a revision at least as new.
- A failure opened by any configured verifier is clearable by the harness, not just one opened by the first entry.
- Two settlements at the same moment get different order numbers.
- A session with an existing open failure still clears after one pass.
- No evidence observation writes to `event_sequence`.
- A configured command that cannot match warns once and does not block a later valid entry.
- `bun run check` passes, and so do the core effort tests.

## Remaining risks and decisions

| Risk or decision | Impact | Disposition |
| --- | --- | --- |
| Store surface: seven methods with a sequence claim | Not a risk; a consequence of the approved ordering rule | Decided. A counter claimed per observation inside the transaction, before the policy runs, requires a separate claim step, because one write cannot both allocate and use the number |
| Store calls inside `db.transaction` join that transaction | High if wrong | Mechanism verified in source; proven by the Task 3 concurrency and rollback tests |
| SQLite serialization under concurrent claims | High if wrong | Proven by the eight-claim test on the temp-file layer, within one connection |
| A verifier that opened a failure and is later removed from the configuration | Medium | Accepted: the failure stays open and the session stays dirty. Recovery is editing the config back or opening a new failure with a configured command |
| A failed write still invalidates a clean pass | Low | Accepted; it only delays a step-down |
| Harness selection changes for configs whose first entry is invalid | Low | Covered by Task 4 acceptance and the load-time warning |
